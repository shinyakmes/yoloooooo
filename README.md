## 1. 数据这摊事

### 1.1 NEU-DET 

东北大学热轧带钢表面缺陷库，6 类：`crazing`（龟裂）、`inclusion`（夹杂）、`patches`（斑块）、`pitted_surface`（麻点）、`rolled-in_scale`（压入氧化皮）、`scratches`（划痕）。

我用的是带**原始 VOC XML 标注**的公开镜像。
具体原因是：我想实现自主转换和划分，以及下载、审计、转换全在本仓库脚本里，任何一步都能重跑。

### 1.2 审计环节（`scripts/audit_dataset.py`）


| 项目 | 结果 |
|---|---|
| 图像数 / 标注数 | 1770 / 1770（0缺失、0未匹配**） |
| 图像尺寸 | 全部 200×200 |
| 标注框总数 | 4126 |
| 单图目标数 | 1–9 个，中位数 2 |
| 框面积（占全图） | 中位数 11.8%；<0.5% 的极小框只有 1 个；>80% 的整片框 115 个 |
| 退化框 / 越界框 | 0 / 0 |

**两个发现直接改了我后面所有决定：**

1. **图像级均衡 ≠ 实例级均衡**。每类图片 294–296 张，看着几乎完美均衡；但框数差了 **2.4 倍**（`inclusion` 1001 个 vs `pitted_surface` 423 个）。训练时类别损失是按框加权的 —— 所以到时候弄类别加权会不均衡，看图片数会看走眼。
2. **图只有 200×200**。用 `imgsz=640` 等于 多乘3.2 倍上采样，把算力花在插值出来的像素上。所以后来我专门做了 640 vs 320 对照。

## 2. 关于为什么是 YOLOv8

| 方案 | 在产线上的真实情况 | 本人判断 |
|---|---|---|
| 传统 OpenCV（阈值 / 边缘 / 模板） | 光照一变、材质批次一换，视觉方案就得整改；缺陷形态多变时规则会爆炸 | 能当基线，当主方案不稳 |
| 两阶段（Faster R-CNN 系列） | 精度更高，但推理慢、部署重，产线节拍吃不消 | 不适合实时场景 |
| **单阶段 YOLOv8** | 速度与精度平衡、生态成熟、导 ONNX/TensorRT 方便 

NEU-DET 这类缺陷与背景灰度接近、边界模糊的图，瓶颈根本不在网络结构创新，而在数据质量 或者 工作点选择上面，毕竟硬伤没办法改变，那就尝试其他情况嘛。

### 3.1 评测协议 v2：5 折交叉验证 + 固定测试集 + 2σ 判断线

**为什么要有这个协议**：做这件事之前，我不知道"多大的差异才算数"。现在量出来了 ——
换数据划分（5 折，固定同一个测试集）的总指标波动 **σ = 0.0126**、判断线 **0.025**；
而单类 `crazing` 的 σ 高达 **0.0511**、判断线 **0.102**。
在此之前，±0.01 的"提升"根本无法判断真假 —— 之前那几个对照实验的结论全都受这个限制。

| 规矩 | 内容 |
|---|---|
| 折划分 | train+val 共 **1595** 张，按类别分层（seed `20261119`）分 5 折；**test 175 张完全不参与** |
| **校验（三层）** | ① **硬性**：每折 train∩val=0、5 折 val 并集=1595、每张图恰好被验证 1 次、test 零泄漏；② **图片数分层**：每类每折 52–54 张（理想 53.2），最大相对偏差 **1.5%**；③ **框数抖动**：最大相对偏差 **10.5%**（分层只管得到"图"这一层），且与 AP 波动无对应关系。完整表格与判据见 [`docs/交叉验证协议.md`](docs/交叉验证协议.md) |
| 配置 | 每折逐项相同：yolov8n / 640 / 50 轮 / batch 16 / seed 0 / workers 2 / cache False |
| **评测** | **每折模型都在同一个 175 张测试集上评一次** → 5 个可配对的值 |

```powershell
E:\yolo\venv\Scripts\python.exe E:\yolo\repo\scripts\verify_kfold.py           # 三层校验：互斥/完备/分层/框数
powershell -ExecutionPolicy Bypass -File E:\yolo\repo\scripts\run_cv.ps1       # 跑 5 折（断点续跑）
E:\yolo\venv\Scripts\python.exe E:\yolo\repo\scripts\eval_cv_test.py --prefix cv  # 汇总：均值±标准差
```

**判据**：差异 < **2σ** → 只能写"未观察到可区分差异"；≥ 2σ → 再逐折配对比较（看 5 个差是否同号）。

**实测噪声底（yolov8n / 640 / 50 轮 / seed 0，5 折 × 同一个 175 张测试集）**：

| 指标 | 均值 | 标准差 | 最小 / 最大 | **2σ 判断线** |
|---|---|---|---|---|
| **test mAP@0.5** | **0.7900** | **0.0126** | 0.7681 / 0.7986 | **0.0252** |
| test mAP@0.5:0.95 | 0.4376 | 0.0114 | 0.4200 / 0.4514 | 0.0229 |

逐折：0.7908 / 0.7973 / 0.7681 / 0.7986 / 0.7950

分类别 AP@0.5（跨折均值 ± 标准差）：

| 类别 | 均值 | 标准差 | **2σ 判断线** | 读法 |
|---|---|---|---|---|
| **crazing** | 0.4642 | **0.0511** | **0.1021** | ⚠️ 单独一档的不可靠 |
| rolled-in_scale | 0.7097 | 0.0271 | 0.0543 | 次不稳定 |
| pitted_surface | 0.8670 | 0.0254 | 0.0507 | |
| patches | 0.9246 | 0.0159 | 0.0318 | 稳 |
| inclusion | 0.8496 | 0.0146 | 0.0292 | 稳 |
| scratches | 0.9248 | 0.0109 | 0.0217 | 最稳 |

**三条要记住的结论**：

1. **真实的噪声底比之前以为的窄得多**：总 mAP@0.5 的标准差只有 **0.0126**，判断线 **0.025**。
   之前写"折间波动 0.6579–0.7780、宽度 0.12"是**错的** —— 那个范围混进了被中断的折、
   不同模型、以及各折**不同**的 val 集，不是同一口径下的噪声。
2. **crazing 的 2σ 高达 0.102**，是总指标的 4 倍。也就是说：
   **关于 crazing 的任何单类结论，差异小于 0.10 的一律不可信**。
   这直接解释了为什么围绕这一类折腾了很久却没有定论 —— 不是方法不对，是**测量分辨率根本不够**。
3. **单次 0.8055 vs 5 折 0.790 并不矛盾**：单次那组用 1416 张训练，而每折只有约 1276 张（80%）。
   两个数口径不同，都真实。**报告里应该写 5 折的 0.790 ± 0.013**，因为它带不确定度。

> **旧 k-fold 的结论作废**：`kfold_f2/f3` 的权重是 31.8 MB（优化器未剥离）= 中途被杀的残局，
> `kfold_f4` 从没跑过 —— 实际只有 2 折；而且旧汇总读的是各折**不同**的 val 集，5 个数字不可配对。
> 详见 [`docs/实验记录.md`](docs/实验记录.md) 第 25 条。

## 4. 结果

### 4.1 主结果（测试集，两种口径都摆出来）

| run | imgsz | best ep | mAP@0.5 | mAP@0.5:0.95 | P@0.25 | R@0.25 | 漏检@0.25 |
|---|---|---|---|---|---|---|---|
| **baseline_640** | 640 | 49 | **0.8055** | 0.4339 | 0.6386 | **0.7736** | **22.64%** |
| cmp_320 | 320 | 50 | 0.7988 | **0.4501** | **0.7060** | 0.7289 | 27.11% |

- `mAP` 是框架标准评测（conf=0.001，全 PR 曲线积分）；
- `P / R / 漏检 @0.25` 是我自己尝试写的匹配器（`scripts/eval_pr_at_conf.py`）：conf=0.25、IoU≥0.5、按类别按置信度贪心匹配。

**两种分辨率没有决定性差异**：mAP@0.5 差 0.007，mAP@0.5:0.95 反而 320 略高。175 张测试集 / 402 个框，这点差值就在噪声里。
能站得住的结论只有一句：**320 用一半算力拿到同等精度**（吞吐 1.23 vs 2.96 ms/图），640 在固定阈值下召回略高。

> 320和640各有千秋

### 4.2 分类别：问题是谁

| 类别 | AP@0.5 | 漏检率 @conf0.25 | 我的观察 |
|---|---|---|---|
| scratches（划痕） | **0.9345** | 11.11% | 长条高对比，最好检 |
| patches（斑块） | 0.9109 | 8.24% | 面积大、特征明显 |
| inclusion（夹杂） | 0.8697 | 17.02% | 点状深色，比较稳 |
| pitted_surface（麻点） | 0.8516 | 24.44% | 密集小点，边界糊 |
| rolled-in_scale（氧化皮压入） | 0.6996 | 34.43% | 与背景灰度接近 |
| **crazing（龟裂）** | **0.5670** | **47.62%** | 细密网状浅纹理，最难搞 |

`crazing` 和 `rolled-in_scale` 扛下了大部分 FN。这是 数据性质 决定的（浅纹理、低对比、没明确边界），不是训崩了。
把指标按类别拆开，你才知道下一步该补哪类数据 —— **这是我认为这个项目里最有价值的一条结论**，比总分好看更值钱。

### 4.3 速度：一个我没想到的结果

| imgsz | batch=1 单帧 | batch=16 每图 | batch=16 吞吐 |
|---|---|---|---|
| 640 | 16.51 ms | **2.96 ms** | 338 img/s |
| 416 | 15.56 ms | 1.17 ms | 853 img/s |
| 320 | 17.10 ms | 1.23 ms | 813 img/s |
| 192 | 16.50 ms | 0.98 ms | 1017 img/s |

**batch=1 时，延迟在 192→640 之间几乎不动，都是 16.5 ms 左右。**

我第一次测完以为表坏了：不是说 320 的算力只有 640 的四分之一吗？
测到 batch=16 才看清 —— **单帧瓶颈根本不是卷积算力，是框架开销**（ultralytics 逐层 Python 前向 ≈100 次 kernel launch，约 13 ms）。真正的算力差异要吃饱了才显现：640 比 320 慢 2.4 倍。

完整推理链路实测（`scripts/detect.py`，含解码/NMS/画框/写视频）：

| 场景 | 结果 |
|---|---|
| 175 张测试图逐张推理 | 487 个框，p50 17.9 ms/张，26.9 FPS |
| 175 帧演示视频（500×500） | 414 个框，均值 19.6 ms/帧，**50.9 FPS** |

> 想压单帧延迟，正确方向是导 ONNX / TensorRT 去掉那层 Python 循环 —— 而不是继续往下调 imgsz。这条我还没做，见第 8 节。

### 4.4 工作点分析：漏检 vs 误判

产线上这两类错误成本不对称：**漏检 = 坏件流出去，误判 = 人工回头复检一次**。所以我不给单一数字，给一条曲线。

| conf | TP | FP | FN | precision | recall | 漏检率 | 图像级漏检率 |
|---|---|---|---|---|---|---|---|
| 0.05 | 374 | 917 | 28 | 0.2897 | 0.9303 | **6.97%** | 14.29% |
| 0.10 | 356 | 501 | 46 | 0.4154 | 0.8856 | 11.44% | 21.71% |
| 0.15 | 339 | 330 | 63 | 0.5067 | 0.8433 | 15.67% | 29.14% |
| 0.20 | 328 | 240 | 74 | 0.5775 | 0.8159 | 18.41% | 33.71% |
| **0.25** | 311 | 176 | 91 | 0.6386 | 0.7736 | **22.64%** | 37.71% |
| 0.30 | 301 | 129 | 101 | 0.7000 | 0.7488 | 25.12% | 41.14% |
| 0.40 | 278 | 76 | 124 | 0.7853 | 0.6915 | 30.85% | 47.43% |
| 0.50 | 254 | 49 | 148 | 0.8383 | 0.6318 | 36.82% | 53.14% |
| 0.60 | 221 | 21 | 181 | 0.9132 | 0.5498 | 45.02% | 61.71% |

**这张表怎么用：**
- 安全优先（宁可多判）：conf≈0.10，漏检 11.4%，代价是每 10 个报警里大概 4 个是真的；
- 人手紧张（报警即准）：conf≈0.50，precision 0.84，但漏检飙到 36.8%；
- **不存在又低漏检又高精度的点** —— 想两头都要，只能回去改模型或改数据（见第 8 节）。

> **这里我翻过一次车，值得记下来。**
> ultralytics 的 `val()` 返回的 `box.mp / box.mr` 是 **PR 曲线上 F1 最优点**的值，不是你在 `conf=` 里传的那个阈值。
> 我拿 conf=0.05…0.20 扫了一圈，返回的数字**一模一样**，才发现这事。第一版报告因此写下错结论："降低阈值换不来召回"。
> 自己写匹配器之后纠正为：**降阈值确实能换召回，代价是误判暴涨**。
> 教训：框架给的汇总数字很方便，但它未必在回答你问的问题。详见 [`docs/实验记录.md`](docs/实验记录.md) 第 14 条。

## 6. 我踩过的坑

完整版 16 条在 [`docs/实验记录.md`](docs/实验记录.md)，这里挑最能说明问题的 7 条：

1. **文献都说 NEU-DET 有 1800 张，我这批镜像只有 1770 张。** 逐文件配对验完（零缺失、零不匹配）之后我接受了 1770，README 里也写 1770。数字要能对得上日志，不是对得上文献。
2. **PowerShell 和 curl 的 HTTPS 全挂，pip 却能下 2.5 GB。** `Invoke-WebRequest` 报连接关闭、curl 报 `Schannel SEC_E_NO_CREDENTIALS` —— PowerShell 5.1 用 TLS 1.0、curl 走 Windows Schannel 拿不到凭证，而 Python 用自己的 OpenSSL。**结论：这台机器上所有下载都改走 Python 通道。**
3. **ultralytics 8.4 训练前会偷偷下 `yolo26n.pt` 做 AMP 校验**（日志写着 "for AMP checks, not used for training"）。慢网下它卡在 14 KB/s，训练迟迟不开始。手动把这个文件预置到 weights 目录就好了。
4. **torch 下完 2.5 GB 进程被杀，靠 pip 缓存 161 秒重装完成。** 从半小时变成两分钟，只因为缓存放在大容量盘上。
5. **框架的 `box.mr` 骗了我一次**（见 4.4 末尾）。这条最贵 —— 它让我的结论错了一版。
6. **视频分支报"检测到 0 个目标"，而同一模型跑图片正常。** 查了半天发现 `n_obj += 1` 被我写在了 `if writer:`（开了 `--save-csv` 才进）里。**统计代码的 bug 长得特别像模型 bug。**
7. **val 0.7605 / test 0.8055。** 一开始以为是哪里错了，后来想明白：175 张测试集，波动本来就大。所以报指标必须写清"哪个集、多少样本"。

## 8. 还没做的
- **`crazing` 是全项目唯一的短板**：5 折 AP@0.5 = **0.4642 ± 0.0511**，其余 5 类在 0.71–0.92。
  诊断结论（`实验记录.md` 第 22 / 24 条）：误差主要在**框中心偏移**而不是框偏大偏小，且整体置信度低。
  也就是说，"紧贴的矩形框 + 单一置信度"这个输出形式，对这类弥散纹理缺陷本身就错配。
  **改进方向是换输出形式（分割 / 图块级判定），而不是继续调 YOLO 的检测头。**
- **没做 TensorRT**：ONNX 已导出并与 pt 逐框验证等价（§4.6），ORT 线程配置也测清了
  （默认 238.7 ms → 8 线程 48.0 ms），但 TensorRT / FP16 没做
- **没做超参搜索**：数据增强、lr 调度、类别加权各只试了一两个点（`exp_mosaic0` / `exp_clspw`），
  没做系统搜索。被问"你怎么把 mAP 调上去的"，我的回答是：**没调上去** ——
  反而通过 5 折发现，之前以为的那些"提升"基本都在噪声里
- **结构对照只做了 v8n vs v8s**（结论：无可分辨差异），注意力模块、其他检测器没试
- **CLAHE 只做了单次对照**（0.7570 vs 0.7623，落在噪声内；见第 23 条），还没走 5 折配对
- **没在真实产线视频上验证**（数据集是离线图像，演示视频是合成流）
- **没做部署服务化**：目前是脚本推理 + ONNX 单帧基准，没有服务端/客户端，也没有相机接入

## 9. 后记
卧槽感谢你看完我的答辩项目，那么这个时候就有人要问了
Q：为什么用 YOLOv8 而不是 Faster R-CNN？
A：产线走节拍。两阶段精度可能更高，但推理和部署都重；传统阈值法对光照和材质批次太敏感。这个数据集的瓶颈也不在结构，在数据和阈值。

Q：0.806 是在哪测的？
A：独立测试集，175 张、402 个框，训练和调参全程没碰过。验证集上是 0.7605 —— 两者差 0.045，因为测试集小、波动大。

Q：漏检 22.6% 能接受吗？
A：不能单独看。conf 降到 0.05 时漏检 7.0%，但精确率掉到 0.29（每 10 个报警只有 3 个真）。实际用哪个值，取决于漏检和人工复检哪个更贵把

Q：你怎么发现问题的？
A：最典型的一次是框架返回的 P/R 不随我传的 conf 变化，扫了几个阈值数字完全一样，才查出它给的是 F1 最优点。之后自己写了匹配器，也顺手纠正了一个错误结论。

Q：为什么把数据集和权重排除在仓库外？
A：仓库应该能 clone 下来一键重建。把 133 MB 数据和 2.5 GB 权重塞进 Git 太几把大了，脚本重跑就行。
