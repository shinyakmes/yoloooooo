## 一、环境搭建

### 1. 系统自带 Python 3.8.5 太老
- **现象**：`python -V` 是 3.8.5；新版 ultralytics 与 torch 都要求 ≥3.9。
- **解决**：另装 3.11，建独立 venv（`py -3.11 -m venv E:\yolo\venv`），不污染系统 Python。
- **注意**：`py -0` 里有 3.11，但 PATH 里的 `python` 仍是 3.8.5 —— 所有命令显式用 venv 解释器，不靠 PATH。

### 2. PowerShell 的 HTTPS 全挂，pip 却能下 2.5 GB
- **现象**：`Invoke-WebRequest` 访问 https 报"基础连接已经关闭"；`curl.exe` 报
  `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`；但 `pip install torch` 正常下 2.5 GB。
- **原因**：PowerShell 5.1 默认 TLS 1.0（被服务端拒绝）；curl 走 Windows Schannel，本机拿不到证书凭证。
  Python 用自己的 OpenSSL + certifi，完全不受影响。
- **解决**：**所有下载改走 Python 通道**（`scripts/fetch_file.py`、`scripts/fetch_dataset.py`）。
  这也解释了"能 pip 装包却下不了数据集"这种看似矛盾的现象。

### 3. torch 下载完成、安装阶段被杀
- **现象**：第一次装 torch 在 2.5 GB 下完后进程被终止，venv 仍是空的。
- **解决**：pip 缓存已经完整（`PIP_CACHE_DIR` 指向大盘），重跑同一命令即从缓存安装，
  **不再重新下载**，161 秒装完。教训：**把 pip 缓存放在大容量盘上，重试成本从半小时变成两分钟**。

### 4. ultralytics 8.4 会偷偷下 yolo26n.pt，卡住训练启动
- **现象**：`yolo train model=yolov8n.pt ...` 卡在 `Downloading .../yolo26n.pt ... 14% 14.0KB/s`。
- **原因**：`utils/checks.py` 的 AMP 校验会下 `yolo26n.pt` 做混合精度兼容性检查，
  日志写明 *"for AMP checks (one-time, not used for training)"*；该域名此刻只有 ~15 KB/s。
- **解决**：自己用 Python 通道把同一文件下到 `weights_dir`，训练启动直接命中本地文件。
- **影响**：只影响启动时间，不影响训练结果。

### 5. 磁盘布局与文件系统（中间搬过一次家）
- **最初**：venv/代码在 D 盘（NTFS），数据集/训练输出/权重/缓存在 F 盘（exFAT，285 GB）。
- **踩到的坑**：exFAT **不支持硬链接**，所以"临时文件 + 硬链接"式的原子写入在 F 盘会失败（报 `EISDIR`），
  文本文件只能写在 NTFS 盘上。这个现象当时看起来像工具 bug，实际是文件系统能力差异。
- **最终方案（2026-11-01）**：**全部迁到 E 盘（NTFS）一个根目录 `E:\yolo\`** ——
  venv / repo / datasets / runs / weights / demo / pip 缓存 都在里面，不再跨盘。
  `yolo settings datasets_dir=E:\yolo\datasets runs_dir=E:\yolo\runs weights_dir=E:\yolo\weights`
- **迁移时的一个真问题**：**venv 不能复制粘贴搬家**。
  `pip.exe`、`yolo.exe` 这类启动器里写死了虚拟环境的绝对路径，换个盘就指向旧位置。
  正确做法是**用 pip 缓存重建 venv**（`E:\yolo\repo\scripts\setup\setup_E.ps1`）：
  缓存里已有 2.5 GB 的 torch wheel，重建只花 **163 秒**，无需重新下载。

## 二、数据

### 6. 公开镜像的实际张数不是"1800"
- **现象**：文献与资料都写 NEU-DET 共 1800 张（6 类 ×300），实际下载的镜像只有 **1770 张**，
  每类 294～296 张。
- **处理**：逐文件配对检查（图↔标注一一对应、零缺失、零不匹配）后**接受 1770**，
  README 写实数，不写"1800"。**简历/README 里每个数字都要能在日志里找到出处。**

### 7. 原始标注是 VOC XML，不是 YOLO txt
- **决策**：不下载别人转好的 YOLO 版本，**自己写转换脚本**（`scripts/convert_voc_to_yolo.py`）。
- **理由**：① 转换过程要能讲清楚（归一化、越界裁剪、退化框丢弃）；
  ② 划分必须可控可复现（分层抽样 + 固定种子），而不是接受别人随手分的。
- **细节**：少数框贴边界，先 clamp 到 `[0,W]×[0,H]` 再归一化；本次丢弃的退化框为 0。

### 8. 图像级均衡 ≠ 实例级均衡
- **审计**：每类图片 294～296 张（几乎完全均衡），但**标注框数差 2.4 倍**：
  `inclusion` 1001 个框 vs `pitted_surface` 423 个框。
- **含义**：按图片数看是均衡数据集，训练时类别损失却**按框数加权**。
  "类别不均衡"不能只看图片数。

### 9. 图像只有 200×200
- **含义**：`imgsz=640` 是 **3.2 倍上采样**，算力花在插值出来的像素上。
- **处理**：先按文献惯例跑 640 作参照，再跑 **320**（1.6 倍）做速度/精度对照，
  用真实数据决定部署尺寸。

## 三、训练与评测

### 10. 训练日志看不到进度
- **现象**：`yolo train ... | Select-Object -Last 80` 把输出全缓冲，跑完才吐。
- **解决**：`cmd /c "... > run.log 2>&1"` 落文件，另用 `results.csv` 做机器可读监控。

### 11. 验证集与测试集指标差得比较多
- **现象**：best epoch 的 **val** mAP@0.5 = 0.7605，**独立测试集**上 0.8055。
- **原因**：测试集只有 175 张，指标波动大。**报告指标必须写清哪个集、多少张图。**
  反过来这也是"必须留独立测试集、不能拿测试集调参"的实证。

### 12. 漏检率：不给置信度阈值就没有意义
- **现象**：同一模型 conf=0.25 时框级漏检 22.64%；降到 0.05 漏检只有 6.97%，但误判率从 36% 涨到 71%。
- **处理**：单独做工作点分析（`scripts/eval_pr_at_conf.py`），
  报"为达到 X% 漏检预算需 conf 取多少、此时误判率多少"。产线上这是**成本权衡**。
- **与实习的衔接**：OPT 实习做的正是"误判 50 台里错 10 台压到 4～5 台"这类工作点调整。

### 13. 分类别看，龟裂（crazing）最难
- 测试集 AP@0.5：`scratches` 0.9345 > `patches` 0.9109 > `inclusion` 0.8697 >
  `pitted_surface` 0.8516 > `rolled-in_scale` 0.6996 > **`crazing` 0.5670**
- 漏检率（conf 0.25）：`crazing` **47.62%**、`rolled-in_scale` 34.43%，两者合计贡献了大部分 FN。
- 原因方向：龟裂是细密网状浅纹理，与背景灰度差异小、无明确边界；划痕是长条高对比目标。
- 这是"用数据发现问题"的证据，比空谈"做了个检测系统"有内容。

### 14. ⭐ 框架返回的 precision/recall 不是"你设的那个 conf"下的值
- **现象**：用 `model.val(conf=X)` 扫 X=0.05/0.10/0.15/0.20，返回的 `box.mp / box.mr`
  **四位小数完全相同**。按这个结果我第一版写下了错误结论："降低阈值换不来召回，说明漏检是模型能力问题"。
- **原因**：ultralytics 返回的 `mp / mr` 取自 **PR 曲线上 F1 最优点**，不是传入的 conf 阈值。
  阈值只影响曲线参与计算的点，不影响默认汇报的那个点。
- **纠正**：自己写匹配器（`scripts/eval_pr_at_conf.py`）：先以 conf=0.01 出全部预测，
  再按指定阈值过滤 + 按类别按置信度贪心匹配（IoU≥0.5，GT 只能被匹配一次）。
  真实曲线是"降阈值确实能换召回，代价是误判暴涨"（conf 0.05→0.25：漏检 6.97%→22.64%，precision 0.29→0.64）。
- **教训**：**指标口径要自己验证**。框架给的汇总数字方便，但它可能回答的不是你问的问题；
  进报告/简历的数字必须有自己可控的实现。

### 15. 视频分支"检测数为 0"——统计 bug，不是模型问题
- **现象**：演示视频 175 帧跑完，汇总里 `detections = 0`；同权重跑测试图却正常出 487 个框。
- **原因**：`n_obj += 1` 被写在了 `if writer:`（开了 `--save-csv` 才有）分支里面，
  不导 CSV 就永远不计数。检测与画框本身都正常（抽帧确认框和标签都在）。
- **教训**：**统计代码的 bug 看起来像模型 bug**。先分区判断"是功能坏了还是日志坏了"。

### 16. ⭐ batch=1 的延迟几乎不随 imgsz 变化
- **现象**：imgsz 从 640 降到 320 甚至 192，单帧前向延迟都在 16.5 ms 左右，
  一开始怀疑"320 的对照实验白做了"。
- **原因**：用 CUDA events 测 batch=16 才看清：640 是 2.96 ms/图，320 是 1.23 ms/图（**2.4 倍差**）。
  也就是说 batch=1 时 ~13 ms 是框架开销（ultralytics 逐层 Python 前向 ≈100 次 kernel launch），
  卷积算力只占 ~3 ms。
- **教训**：**测"延迟"和测"算力"是两件事**。batch=1 测到的是框架开销；
  要报速度就同时给 batch=1 延迟和饱和吞吐，否则数字没法解释。
- **推论**：想压单帧延迟，方向是导出 ONNX/TensorRT，不是继续调 imgsz。


### 17. DataLoader worker exited unexpectedly（Windows 多进程的经典崩法）
- **现象**：直接跑 `yolo train ...`（没指定 workers）时报
  `RuntimeError: DataLoader worker (pid(s) ...) exited unexpectedly`，训练在第一批就死。
- **原因**：ultralytics 默认 `workers=8`，在 Windows 上要 spawn 8 个进程做数据加载；
  一旦某个 worker 起步失败（内存紧张、句柄、沙箱限制），主进程就直接报错退出。
- **解决**：显式指定更小的 `workers=4`（或 2）。我们训练成功的那两次都带着 `workers=4`；
  我用默认 8 复现了失败，改成 2 后立刻正常。
- **教训**：`workers` 不是"越多越快"——它是**数据预取的进程数**，
  在这个数据规模（1416 张 200×200）下 4 个绰绰有余，调大只会增加崩溃概率。
- **顺带**：`data.yaml` 里不要写绝对路径。省略 `path:` 时 ultralytics 以 yaml 所在目录为根，
  换盘搬家不用改文件（我们搬过一次家，就是因为写死的 `F:/yolo/...` 导致训练报"images not found"）。

**第二次（真相）**：跑 seed=1 对照时又崩，这次的报错把根因写清楚了：

```
RuntimeError: Caught MemoryError in DataLoader worker process 3.
  ...
numpy._core._exceptions._ArrayMemoryError: Unable to allocate 4.69 MiB
  for an array with shape (1280, 1280, 3) and data type uint8
```

连 4.69 MiB 都分配不出来 → **主机内存（RAM）耗尽**，不是显存。
这台笔记本只有 **15.6 GB** 内存，平时 Edge（4 个进程）+ QQ + Steam 就吃掉 2~3 GB；
而 `cache=True` 会把 1416 张图缓存进内存，Windows 上 `workers` 又用 spawn，
每个 worker 都是完整 Python 进程、各自一份运行时 —— 4 个 worker 就能再吃掉 2~3 GB。

**最终解法**（三条一起）：
1. `workers=2`（甚至 1）
2. `cache=False`（图很小，16 KB/张，重读盘的代价远小于内存爆炸）
3. 训练前关掉浏览器 / QQ / Steam，能多出 2~3 GB

**教训**：
- `MemoryError`（numpy）= **主机内存**；`CUDA out of memory`（torch）= **显存**。两个完全不同的资源，报错文本就能区分。
- 看到 "worker 崩了" 别急着怪进程数：**先看它是因为什么崩的**。信息不足时（第一次那种只有 `exited unexpectedly`）
  只能靠试；信息充足时（这次直接给了 `MemoryError`）就照着根因修。
- 同一个现象两次出现，未必同一个原因 —— 第一次的结论当时成立，但不够深。

### 18. git push 连不上 / Schannel 断流 —— 换 OpenSSL 后端就好了
- **现象**（三种都遇到过）：
  1. `git push` → `Recv failure: Connection was reset`
  2. 开了代理 → `schannel: server closed abruptly (missing close_notify)`
  3. 加 `http.proxy` → `TLS connect error: error:0A000126 ... unexpected eof while reading`
- **诡异点**：`git ls-remote` 和 `git fetch` **一直是通的**，只有 push 挂 —— 说明不是"全面断网"，
  而是推送方向（带认证的 POST）被单独干扰。
- **根因**：Git for Windows 默认用 **Schannel**（Windows 原生 TLS）做 HTTPS，经过代理/TUN 时握手容易被打断。
- **解法**：换成 OpenSSL 后端，一条命令：

  `powershell
  git config --global http.sslBackend openssl
  git push -u origin main
  `

  实测：换成 openssl 后**直接推成功**（`d41bd3b..16d9720 main -> main`），连代理都不用显式配。
- **教训**：
  - "拉得下来推不上去"是典型症状，别急着怀疑账号权限 —— 先看 TLS 后端。
  - Windows 上的 curl / Invoke-WebRequest / git 默认都可能是 Schannel；Python 和 OpenSSL 后端通常更稳。
  - 这个环境里凡是"HTTPS 莫名失败"，第一反应应该是"换个 TLS 实现再试"。

### 19. ONNX 导出：模型等价，但 CPU 上的"默认配置"慢 5 倍
- **做了什么**：`best.pt` → ONNX（3 秒，12.2 MB，opset 17），并验证导出后模型是否等价。
- **等价性证据**（不是"看着差不多"，是逐框比）：同一张图 batch=1

  `
  PyTorch  96 个框   最高分 0.2738
  ONNX     96 个框   最高分 0.2736
  逐框 IoU：最小 0.9985 / 中位 0.9997 / 最大 1.0000
  置信度最大差：0.00024
  `

- **延迟实测**（batch=1 纯前向）：

  | 后端 | ms/图 |
  |---|---|
  | PyTorch GPU | 16.5 |
  | PyTorch CPU | 67.5 |
  | ONNX Runtime CPU（默认线程） | **238.7** |
  | ONNX Runtime CPU（8 线程） | **48.0** |

- **坑在哪**：第一反应是"ONNX 导出后更慢"，差点写进结论。实际是 **ORT 默认线程数**问题 ——
  这台机器 20 个逻辑处理器，ORT 默认按核心数开线程，对小模型属于过度并行，线程争抢把收益吃光。
  显式设 `intra_op_num_threads=8` 后 48 ms，**比 PyTorch CPU 快 1.4 倍**。
- **教训**：
  - "某个后端更慢"之前，先确认它的**默认配置**是否适合这个模型规模。
  - 小模型 + 多核 → 线程数不是越多越好，8 比 auto(20) 快 5 倍。
  - ONNX 的真正意义是**脱离 PyTorch/Python 部署**（C++/C#/工控机）+ 接 TensorRT，不是在本机提速。

- **一处未解决（如实记）**：`yolo val` 对 ONNX 报 mAP@0.5 = 0.791，PyTorch 报 0.806。
  已排除 simplify / opset / device / batch，且单图逐框一致 → 模型等价，差异在验证流程。
  没查到底，不编原因。

### 20. crazing 漏检高：现象、初步归因，以及**待验证的改进方向**
- **现象**：crazing 分类别 AP@0.5 只有 0.567，框级漏检 **47.6%**；而 scratches 漏检 11%、patches 8%。
- **观察到的机制（看图 + 看标注得出）**：这类缺陷的标注是**"整片纹理框一个大框"**
  （crazing_1.xml 的框是 (2,2)-(193,194)，覆盖全图 96%），因为整片纹理没有明确边界，
  标注者也难以标得更细；而模型倾向预测**局部子区域**，于是 IoU ≈ 0.20，
  达不到 0.5 的命中门槛 —— 即使模型"看到了缺陷"，在这个口径下也判不对。
- **老师给的意见**（原话大意）：
  1）YOLO 就是框标注任务，绝大多数数据集都是那样标注 —— 所以**标注方式本身没问题**；
  2）从分类别结果看，其他类别"不算很好但也不差"，说明训练流程没有大问题，**问题集中在这一类**；
  3）**下一步建议专门针对这一类做改进和优化**（换更大模型、针对该类优化），把它的检测效果提上来。
- **因此本条的定位**：这是一个**待改进的重点**，不是"范式天花板"、也不是"可以不做"。
  之前把结论写成"固有限制、停止投入"是过度解读，已修正。
- **已验证/待验证的改进路线**：
  - ✅ 已做对照：yolov8n 50 轮 vs 100 轮；yolov8s 100 轮（见 README 4.x 的对照表）
  - ⏳ 待做：针对低对比纹理的预处理（CLAHE）、该类别的数据增强、
    以及老师提的"换更大模型"（v8m 起）
  - ❌ 老师明确认为**过采样意义不大**；我原计划的"按轮次多采样该类"已放弃
  - ❌ 更高输入尺寸无意义：原图仅 200×200，放大只是插值（640 vs 320 已验证差异在噪声内）
- **面试口径（修正版）**：
  > "龟裂这一类 AP 只有 0.567。它的标注是整片一个大框、纹理对比度低，
  > 我分析是模型倾向预测局部导致 IoU 上不去。
  > 现在在按老师的建议做针对性改进：加轮数、换更大模型，并试对比度增强等预处理，
  > 用同一个测试集口径对比。"
- **重要**：这条只涉及归因与下一步计划，不改变此前的任何指标与 badcase 结论。

### 21. 后台训练别关终端窗口（会连带杀进程）
- **现象**：v8s 100 轮训练跑到第 88 轮时，误关控制台窗口，python 进程随即消失。
- **损失**：只有当前轮作废；`last.pt` 每轮都存，用 ``yolo train resume model=weights/last.pt``
  可从断点续训（含优化器状态），不必从头再来。
- **教训**：训练必须保留 ``last.pt``（不只是 ``best.pt``）；长训练尽量挂在独立进程/后台任务里跑，
  不要依附于某个会被关掉的终端窗口。

### 22. ⭐ crazing 漏检的真正机制：不是"框偏小"，是"框中心在飘"——**第 20 条的归因被自己的数据推翻**

**背景**：第 20 条当时把 crazing 漏检 47.6% 归因为"模型倾向预测局部子区域，与整片大框的 IoU≈0.20"。
这个说法一直没有被量化验证过，只是"看图 + 看标注得出的印象"。用 `scripts/diag_boxscale.py` 复测后，结论变了。

**方法**（关键在"选哪个框来评价"）：
按置信度从高到低**贪心认领**还没被认领的同类 GT（IoU≥0.1 才算认领）——这就是部署时模型真正报出来的框。

> ⚠️ **第一版写错了，记下来**：一开始对每个 GT 在"最多 300 个候选"里挑**最像的那个**，门限给到 0.001。
> 结果 crazing 面积比中位 **1.07**、100% 的 GT 都能配上对，看起来"框完全正确"。
> 那是**上界**不是**实际**：300 个框的候选池，模型总能猜中一个。
> **评价模型必须用"模型主动报出的框"，不能用"它能猜到的最好框"。**

**结果**（conf≥0.25 档，测试集）：

| 类别 | 认领率 | 面积比中位 | 中心偏移中位 | IoU 中位 |
|---|---|---|---|---|
| **crazing** | 79.4% | **1.08** | **0.192** ⚠️ | **0.581** |
| rolled-in_scale | 88.5% | 0.96 | 0.133 | 0.698 |
| patches（对照） | 95.3% | 1.01 | **0.049** | 0.836 |
| scratches（对照） | 94.4% | 1.01 | 0.071 | 0.788 |

（中心偏移以真框自身宽/高归一化；0.192 ≈ 中心偏了将近 1/5 个框宽）

**修正后的机制**：
1. **模型看得见** —— 认领率 79%，面积比 1.08，尺度是对的，不是"只框住了局部"。
2. **错在定位漂移** —— 中心偏移 0.192，是 patches 的 **4 倍**。
3. ~~**为什么漂 20% 就致命** —— crazing 的 GT 是覆盖整图 96% 的大框，框越大同样比例的偏移损失越多。~~
   **这条也是错的，见第 4 点。**
4. **⚠️ 二次修正：我又拿一个样本当成了整类规律。**
   实测 crazing 测试集 GT 框面积：中位 **19.3%**、p90 37.9%、**>80% 整图的只有 1.6%**。
   `crazing_1` 那个 96% 的框是**离群样本**，不是这一类的典型形态。
   更硬的反证：**GT 框最大的类恰恰是 pitted_surface**（中位 60.2%，28.9% 的框 >80% 整图），
   而它中心偏移只有 **0.038**、AP@0.5 **0.895** —— **框大根本不是定位不准的原因。**
   所以机制只剩一句：**纹理越浅、边界越不清晰，框的中心就越不确定。**
   变量是对比度 / 边界可辨识性，**不是框的大小**。

**连带否掉一条路**：`yolov8s`（100 轮）crazing 中心偏移 **0.252**，比 `yolov8n`（50 轮）的 **0.192** 更差；
总 mAP@0.5 也是 0.7677 vs 0.7891，**没赢**。
所以"换更大模型就能救这一类"在本数据集上**有反证**（注意：测试集 crazing 只有 63 个 GT，波动不小，
只能说"没有观察到收益，且中心漂移更明显"，不能说"证明了更大模型更差"）。

**为什么不继续往"框偏小"方向使劲**：面积比中位 1.08 已经说明尺度不是瓶颈，
继续调 anchor / 加尺度分支的收益预期很低。

**待验证（下一步）**：
- ✅ 已跑：`imgsz` 640 vs 320、`mosaic=0`、`cls_pw`、v8n 50/100 轮、v8s 100 轮、4 折交叉验证
- ⏳ **进行中：CLAHE 对比度增强**（`scripts/make_clahe_dataset.py`，clip=2.0 / tile=8，只改 L 通道，
  labels 逐字节复制 → 单变量）。假设：纹理对比度上去后边界更清晰，中心漂移减小。
- ⏳ 若 CLAHE 无效，再考虑针对整片纹理类的后处理规则（按标注约定把框扩张到整片）——
  但必须写明**这是贴合标注约定的规则，不是模型变强**
- ❌ 更高输入尺寸（原图仅 200×200，放大只是插值；640/320 已验证差异在噪声内）
- ❌ 类别过采样（老师已明确认为意义不大）

**面试口径（再修正版）**：
> "龟裂这一类漏检接近一半。我先怀疑是模型只框住了局部，但量化诊断发现不是：
> 面积比 1.08（尺度对），中心偏移 0.19（是正常类别的 4 倍）。
> 我第二个猜测是'因为它的标注框特别大，大框对中心误差敏感'——
> 这个也被数据否了：实测这一类的 GT 面积中位只有 19%，反而框最大的 pitted_surface 定位最准。
> 所以真正的变量是对比度：纹理越浅、边界越糊，框的中心越不确定。
> IoU 中位卡在 0.58 就掉到 0.5 门槛下 —— 这是定位精度问题，不是检测能力问题。
> 我还试过换更大的模型、也试过 CLAHE 对比度增强，都是负结果，但两次负结果都把这个机制钉得更死了。"

**教训**：
- 一个"看起来合理"的定性归因（第 20 条）可以传好几轮都没被验证。**只要还没量化，它就是猜测。**
- **指标口径要先定义"选哪个预测"**。"最像的那个"和"模型报出的那个"是两个不同的问题：
  前者衡量接近上界，后者才衡量实际表现。
- 换模型、加容量是最容易想到、也最容易白干的动作。**先测清瓶颈在哪（尺度？位置？置信度？），再决定动不动模型。**


### 23. CLAHE 对比度增强对照：**定位确实变准了，但置信度塌得更快，净收益为负**

承接第 22 条。既然测出来 crazing 的病根是"框中心漂移"，那最直接的药就是让纹理边界更清楚。
做了单变量对照：**只换像素，不换划分、不换 GT、不换超参。**

**做法**（`scripts/make_clahe_dataset.py`）：
BGR→LAB，只对 L 通道做 CLAHE（clipLimit=2.0，tileGridSize=8×8），输出无损 PNG；
labels **逐字节复制**（md5 全校验，0 个不一致）。平均亮度 128.23→129.35（均衡保持均值，符合预期）。

**训练**：yolov8n，640，50 轮，batch 16，seed 0，deterministic，workers 2，cache False。
与 `baseline_640` 逐项相同，唯一变量是数据。耗时 **12.4 min**（baseline 14.0 min）。

**测试集结果**（独立测试集 175 张 / 402 框）：

| run | mAP@0.5 | mAP@0.5:0.95 | P | R |
|---|---|---|---|---|
| baseline_640 | **0.8055** | 0.4339 | 0.7438 | 0.7760 |
| exp_clahe_640 | **0.7849** | **0.4406** | 0.7177 | 0.7332 |

分类别 AP@0.5：

| 类别 | baseline | CLAHE | 差 |
|---|---|---|---|
| **crazing** | 0.5670 | **0.4554** | **-0.1116** ⚠️ |
| inclusion | 0.8697 | 0.8547 | -0.0150 |
| patches | 0.9109 | 0.9035 | -0.0074 |
| pitted_surface | 0.8516 | **0.8766** | **+0.0250** |
| rolled-in_scale | 0.6996 | 0.6946 | -0.0050 |
| scratches | 0.9345 | 0.9243 | -0.0102 |

**但中间指标是反方向的**（`diag_boxscale.py`，conf≥0.25 档）：

| 指标 | baseline | CLAHE | 读法 |
|---|---|---|---|
| crazing 中心偏移 | 0.192 | **0.168** | 定位**变准**了 ✅ |
| crazing IoU 中位 | 0.581 | **0.614** | 同上 ✅ |
| crazing 面积比中位 | 1.08 | 1.16 | 框略微变松 |
| **crazing 认领率(conf≥0.25)** | **79.4%** | **57.1%** | 置信度**塌了** ❌ |

**怎么读这三个数字叠在一起**：
1. **假设被验证了一半**：CLAHE 确实压低了中心漂移（0.192→0.168），IoU 中位也上去了。
   这说明第 22 条"病根在定位漂移、且与纹理对比度有关"的判断方向是对的。
2. **但代价更大**：认领率从 79.4% 掉到 57.1% —— 同样的 conf 门限，模型对 crazing 的信心明显下降。
   而 AP@0.5 对召回极度敏感，所以最终 crazing AP 掉了 0.11。
3. **机制猜测（未验证）**：CLAHE 把局部噪声一起放大了，本来"浅纹理"的信息量就没多少，
   放大对比度是等比例放大信号和噪声；同时像素分布偏离了 COCO 预训练的先验，迁移学习吃亏。
   验证办法：只对 crazing 类做 CLAHE、或减小 clipLimit、或用灰度分位数拉伸替代 CLAHE —— 都还没做。

**⚠️ 但总指标这一档必须说清楚：不能拿 -0.021 当结论。**
同配置不同种子的波动范围（val mAP@0.5）：

| 来源 | 范围 |
|---|---|
| 同配方不同种子（seed=0/1） | 0.7249 – 0.7605 |
| `my_640` / `mosaic0` / `cls_pw` / `v8n_100` | 0.7527 – 0.7780 |
| 4 折交叉验证 | 0.6579 – 0.7725 |

**波动幅度 ±0.03 甚至更大**，而 CLAHE 与 baseline 的测试集差值只有 -0.021。
所以正确表述是：
> 总 mAP@0.5 **没有观察到可区分的差异**（差值在种子/折间波动范围内）；
> 但**分类别与中间指标给出了一致方向**：crazing 定位变好、置信度变差，净效应为负。
> mAP@0.5:0.95 反而 +0.007，与"定位更紧"自洽。

**方法论结论（这条比结果本身值钱）**：
> **改善中间指标 ≠ 改善最终指标。** CLAHE 把"框中心漂移"这个我明确指出来的中间指标改善了 13%，
> 却让最终 AP 掉了 0.11。如果我只看中间指标，我会写出一条完全错误的结论："CLAHE 有效"。

**下一步（按性价比排）**：
1. ~~CLAHE 全量~~ → ❌ 已证否（净收益为负）
2. ⏳ 减小 CLAHE 强度（clip=1.0）或只对高置信度低对比样本做 → 看能否只要定位、不牺牲置信度
3. ⏳ 灰度分位数拉伸 / 反锐化掩膜，替代 CLAHE（噪声放大更小）
4. ⏳ 接受现状：对整片纹理类报 AP@0.3（crazing 该口径下 0.73）或做图像级判定，而不是硬攻 IoU@0.5

**面试口径**：
> "为了救龟裂这一类，我做了 CLAHE 对比度增强的对照实验。结果是负的：总 mAP 掉了 0.02，
> 龟裂从 0.567 掉到 0.455。但我没有停在'没用'这个结论上 —— 我继续测了中间指标：
> 中心漂移从 0.192 降到 0.168、IoU 中位从 0.58 升到 0.61，定位确实变准了；
> 同时 conf 0.25 下的认领率从 79% 掉到 57%，置信度塌得更快。所以它不是'无效'，
> 是'定位收益被置信度损失吃掉了'。这个实验让我确认了病根在定位漂移——因为干预这个变量时，
> 漂移真的动了。"

### 24. 指标口径：为什么该给 crazing 报 AP@0.3，而不是硬攻 IoU@0.5

**做法**：不训练、不改模型，只把**同一批预测**在不同 IoU 门限下重新积分（`scripts/diag_class.py`），
看每一类对 IoU 门限有多敏感。数据早就在 `runs/eval/diag_*.json` 里，只是之前没人捞出来看。

**crazing 的 AP 随 IoU 门限变化**（测试集 63 个 GT）：

| run | IoU@0.1 | IoU@0.3 | IoU@0.5 | IoU@0.7 |
|---|---|---|---|---|
| v8n 50 轮 | 0.853 | **0.707** | 0.534 | 0.168 |
| v8n 100 轮 | 0.793 | 0.735 | 0.422 | 0.071 |
| v8s 100 轮 | 0.868 | 0.731 | 0.539 | 0.234 |

**各类"AP@0.3 减 AP@0.5"的落差**（v8n 50 轮）—— 这张表是本节的核心：

| 类别 | AP@0.3 | AP@0.5 | 落差 |
|---|---|---|---|
| **rolled-in_scale** | 0.854 | 0.607 | **0.247** |
| **crazing** | 0.707 | 0.534 | **0.174** |
| patches | 0.946 | 0.908 | 0.037 |
| inclusion | 0.889 | 0.862 | 0.027 |
| scratches | 0.953 | 0.928 | 0.025 |
| pitted_surface | 0.914 | 0.895 | **0.019** |

**落差自己分成两堆**：两个低对比纹理类（0.17–0.25），和四个边界清晰的类（0.02–0.04），
中间没有过渡。这说明瓶颈是**「框画得多准」**，而且只卡在低对比的两类上。

**再排除一个错误解释**（这一步很关键，我差点又写错）：直觉会说"是因为这两类的框特别大"。
实测 GT 框面积占整图比例（测试集）：

| 类别 | 面积中位 | >80% 整图占比 | 中心偏移 | AP@0.5 |
|---|---|---|---|---|
| pitted_surface | **60.2%** | **28.9%** | **0.038** | **0.895** |
| crazing | 19.3% | 1.6% | 0.192 | 0.534 |
| rolled-in_scale | 14.6% | 0.0% | 0.133 | 0.607 |
| patches | 9.4% | 0.0% | 0.049 | 0.908 |
| scratches | 10.0% | 0.0% | 0.071 | 0.788 |
| inclusion | 3.6% | 0.0% | 0.072 | 0.862 |

**框最大的 pitted_surface 定位最准、AP 最高。** 所以"框大 → 对中心误差敏感 → IoU 上不去"这条解释**不成立**。
唯一和定位精度同向变化的是**对比度 / 边界可辨识性**。

**结论（三条，按可信度排序）**：
1. 【硬】报告里应该同时给 **AP@0.5 和 AP@0.3**。只给 @0.5 会让 `crazing`（0.534）和
   `rolled-in_scale`（0.607）显得比实际差；只给 @0.3 又是在掩盖定位精度不足。
   **两个口径一起给，并说明落差的含义**，才是诚实的做法。
2. 【硬】这两类的瓶颈是**定位精度**，不是检出能力（IoU@0.1 下 AP 仍有 0.85–0.87）。
3. 【推断，未验证】起作用的变量是对比度/边界清晰度。CLAHE 试验中中心偏移确实降了（0.192→0.168），
   方向上支持这条，但代价是置信度下降（见第 23 条）。

**为什么这条值得写进报告**：它花的成本是**零训练时间**，产出却是"我知道自己的数字在什么口径下成立"。
面试里被问"你这个 mAP 可信吗"，能答出"分口径看、并且我知道哪一类的哪一类误差占主导"，
比多刷 0.01 的 mAP 强得多。

### 25. ⭐ 评测协议 v2：为什么之前所有"改进"都判不出来，以及怎么修

**问题**：算上种子和折，val mAP@0.5 在 **0.6579–0.7780** 之间晃（宽度 0.12）。
这意味着之前任何 ±0.01 的"提升"都无法判断真假。三个根因：

1. **只有一次划分**：1416/179/175 定死一套，没有任何交叉验证，结论全押在一次偶然上。
2. **旧的 k-fold 其实早就崩了，没人发现**（这就是为什么"4 折"的结论不能信）：
   - `kfold_f0/f1`：`best.pt` 6.5 MB → 优化器已剥离 → 真跑完了；
   - `kfold_f2/f3`：`best.pt` **31.8 MB** → 优化器状态还在 → **中途被杀，没跑完**
     （对上第 21 条：关控制台连带杀进程）；它们的 best epoch 16/30 也只是"死在哪"；
   - `kfold_f4`：**从来没跑过**。
   → 实际只有 2 折可用，却一直按"4 折"记着。
3. **旧汇总口径错**：`summarize_kfold.py` 读的是每折**自己 val 集**上的指标。
   5 折的 val 集是**不同的 5 份数据**，所以那 5 个数字**不可配对** ——
   只能看"晃多大"，没法回答"改动是否有效"。

**协议 v2 的四条规矩**：

1. **折划分固定**：train+val 共 **1595** 张，按类别分层（seed `20261119`）分 5 折；
   **test 的 175 张完全不参与**，只在最后用。
2. **校验先行**（`eval_cv_test.py --verify`）：每折 train∩val = 0；5 折 val 并集 = 1595；
   无图被验证两次；test 不混入。实测全部为 0 —— 划分干净，可以当协议用。
3. **每折配置逐项相同**：yolov8n / imgsz 640 / 50 轮 / batch 16 / **seed 0** / workers 2 / cache False。
4. **每折模型都在同一个 175 张测试集上评一次**（这是 v2 的核心）。
   于是拿到 5 个**可配对**的测试集指标。

**判据（以后每个改动都套这一套）**：

| 量 | 含义 | 怎么用 |
|---|---|---|
| 均值 ± 标准差（5 折，同一测试集） | **噪声底** | 写进报告，替代单次数字 |
| **2 × 标准差** | "不要声称有效"的门线 | 差异 < 2σ → 只能写"未观察到可区分差异" |
| 逐折做差（配对） | 同折、同测试集、只差一个变量 | 差异 ≥ 2σ 后，看 5 个差是否同号；同号则可做符号检验 |

**工具**：

| 脚本 | 作用 |
|---|---|
| `scripts/make_kfold.py` | 划 5 折（已有，思路正确，未改） |
| `scripts/run_cv.ps1` | 跑 5 折（**新增**）：断点续跑 + **完成判定** |
| `scripts/eval_cv_test.py` | 逐折测试集评测 + 均值±标准差汇总（**新增**） |

**「完成判定」这个技巧值得单独记**：不看 exit code（PS 里经常是 0），也不看有没有日志，
而是看 **`best.pt` 是否已剥离优化器（< 10 MB）且日志里有 `Optimizer stripped`**。
一次被杀的训练会留下 30 MB 左右、带优化器状态的残局权重 —— 这正是旧 kfold_f2/f3 的形态。

### 26. Windows PowerShell 5.1：`.ps1` 里的中文必须存成 UTF-8 **带 BOM**

- **现象**：脚本里带中文，直接报一堆看不懂的语法错，比如
  `Unexpected token '鏃?'`、`The string is missing the terminator`、`Missing closing '}'`。
  而且报错位置看着完全正常（明明有引号、明明有花括号）。
- **原因**：Windows PowerShell 5.1 读 `.ps1` 时，**没有 BOM 就按系统 ANSI 代码页（GBK）解码**。
  UTF-8 的中文字节被当 GBK 解 → 变成乱码 → 乱码里可能含引号/括号字节 → **把字符串和语句结构一起截断**。
- **为什么之前没炸**：`train.ps1` 里的中文**只在注释里**，注释即使乱码也还是注释，不参与解析。
  而 `run_cv.ps1` 里的中文在**字符串字面量**里，一乱码就吃了引号 → 解析失败。
- **解决**：把 `.ps1` 存成 **UTF-8 with BOM**（`utf-8-sig`）：
  ```python
  s = open(p, encoding='utf-8').read()
  open(p, 'w', encoding='utf-8-sig', newline='\r\n').write(s)
  ```
  Python 脚本（`.py`）不需要这么干 —— Python 3 源文件默认就是 UTF-8。
- **教训**：
  - 报错位置"明明没问题"时，先怀疑**编码**，别死磕括号。
  - 同一类文件，中文放在注释里能跑、放在字符串里会炸 —— 这不是矛盾，是解码边界不同。
  - 换台机器/换个 shell（PS 5.1 ↔ PS 7）可能表现不同：PS 7 默认按 UTF-8 读，
    **所以"在我这儿能跑"不等于"在别人的 PS 5.1 上能跑"**。

### 27. ⭐ 5 折交叉验证的实测噪声底：**我们之前对"噪声"的判断是错的**

跑完协议 v2（5 折 × 同一个 175 张测试集，yolov8n / 640 / 50 轮 / seed 0），结果如下。

**总指标**：

| 指标 | 均值 | 标准差 | 最小 / 最大 | 2σ 判断线 |
|---|---|---|---|---|
| **test mAP@0.5** | **0.7900** | **0.0126** | 0.7681 / 0.7986 | **0.0252** |
| test mAP@0.5:0.95 | 0.4376 | 0.0114 | 0.4200 / 0.4514 | 0.0229 |

逐折 test mAP@0.5：0.7908 / 0.7973 / 0.7681 / 0.7986 / 0.7950
（各折**自身** val mAP@0.5：0.7725 / 0.7476 / 0.7441 / 0.7703 / 0.7407）

**分类别 AP@0.5**：

| 类别 | 均值 | 标准差 | 2σ 判断线 |
|---|---|---|---|
| **crazing** | 0.4642 | **0.0511** | **0.1021** ⚠️ |
| rolled-in_scale | 0.7097 | 0.0271 | 0.0543 |
| pitted_surface | 0.8670 | 0.0254 | 0.0507 |
| patches | 0.9246 | 0.0159 | 0.0318 |
| inclusion | 0.8496 | 0.0146 | 0.0292 |
| scratches | 0.9248 | 0.0109 | 0.0217 |

**这次测量推翻了什么**：

**① 之前把"噪声"高估了 5 倍。**
我曾写"同配方只换种子/换折，val mAP@0.5 在 0.6579–0.7780 之间、宽度 0.12"。
那是**不同口径混在一起**算出来的：包含被中断的折（f2/f3 残局）、不同模型、以及各折**各自不同**的 val 集。
同一口径（固定测试集）下，真实标准差只有 **0.0126**，判断线 **0.025**。
→ **教训：说"噪声多大"之前，必须先固定评测口径。口径不统一的波动不是噪声，是混杂。**

**② crazing 的不可靠程度是总指标的 4 倍。**
stdev 0.0511 → 2σ = **0.102**。含义：
- 任何关于 crazing 的单类结论，差异 **< 0.10** 一律不可信；
- 回头看：CLAHE 让 crazing 掉 0.112（第 23 条）—— **刚过 2σ 门槛**，是"勉强可分辨"，
  不是"明确证否"；而且那是单次运行 vs 5 折均值，严格说还不算配对比较；
- v8s 与 v8n 的 crazing 差异（0.539 vs 0.534、中心偏移 0.252 vs 0.192）→ **完全在噪声内**，
  当时写"更大模型更差"是过度解读，正确说法只能是"未观察到差异"。
→ **这一类只有 63 个测试 GT，单类 AP 天生不稳。围绕它做的单次实验基本无法定论。**

**③ 单次 0.8055 与 5 折 0.790 并不矛盾。**
单次那组用 1416 张训练；每折只用约 1276 张（1595 的 80%）。
训练集显著变小，指标略低是**预期行为**，不是退步。
→ 报告口径：**5 折 mAP@0.5 = 0.790 ± 0.013**（带不确定度，比单次的 0.806 更可信也更诚实）。

**④ 顺带印证了第 11 条**：每折 test 都比自己的 val 高约 0.03–0.05。
同一现象在 5 折上重复出现 5 次，说明不是偶然 —— val 集（317–323 张）与 test（175 张）的性质不同，
或者 val 参与了"选 best epoch"因而被乐观化了。**报指标必须写清是哪个集。**

**一个自己犯的错（记下来）**：汇总脚本里我按**列号**读 `results.csv`，把第 9 列
`val/box_loss`（约 2.0）当成 mAP 打印了，五折 val 全是 2.x —— 一眼就该看出不对的值却输出到了表里。
→ **读 CSV 必须按列名，不能按列号**；而且"这个数字在物理上可能吗"（mAP 不可能 >1）是最后一道防线。

**下一步（按性价比）**：
1. ⏳ **`seed=1` 的 5 折**（`run_cv.ps1 -Prefix cv_s1 -Seed 1`）—— 把"换折的噪声"和"换种子的噪声"分开。
   预计种子噪声 ≥ 折噪声。
2. ⏳ **CLAHE 也走 5 折**（需先给 CLAHE 版建 kfold 数据集）—— 才能和 baseline 做**真正配对**的比较。
3. ❌ 不再围绕 crazing 做单次实验 —— 分辨率不够，先把"数据量/测试集 GT 数"提上去再说。

### 28. 折划分怎么校验：**分层只控制得到"图片"这一层，控制不到"框"**

**现象**：5 折切完了、训练也跑完了，但我手上只有一句"我按类别分层了"——
这句话没法证明划分是干净的。如果某一折的图或框偏多偏少，指标差异就会被误当成方法差异。

**做法**：写 `scripts/verify_kfold.py`，把校验拆成三层，结论落盘到 `runs\eval\kfold_verify.json`。

| 层 | 检查什么 | 结果 |
|---|---|---|
| ① 硬性 | 每折 train∩val=0；5 折 val 并集=1595；每张图恰好被验证 1 次；test 零泄漏；每折 train∪val=池子 | 全部通过 |
| ② 图片数比例 | 每类每折实际张数 vs 理想值（池内总数÷5） | 52–54 vs 53.2，**最大偏差 1.5%** |
| ③ 框数比例 | 每类每折实际框数 vs 理想值 | **最大偏差 10.5%**（scratches 107 vs 96.8） |

自检：5 折 val 的图片数相加 = 1595 ✓、框数相加 = 3724 ✓，都等于池子总数 → 没有重复计入、没有漏掉。

**为什么框数会晃到 10%**：分层只保证"每折多少张图"，管不了这些图上有几个框。
各类"每图平均框数"差很多：inclusion **3.40**、patches 2.94、crazing 2.31、rolled-in 2.10、scratches 1.82、pitted_surface **1.43**。

**这个 10% 要不要管？不要**，用 crazing 自己当反例：

| 折 | 龟裂框数 | 龟裂 test AP@0.5 |
|---|---|---|
| f0 | **127（最多）** | **0.4386（最低）** |
| f1 | **117（最少）** | 0.5053（第二高） |

框最多的那折成绩最差、框最少的那折成绩还不错 → **crazing 的折间波动不是框数造成的**，
而是它本身性能低（0.46）+ 框边界主观。这条比"框数均衡"本身有信息量。

**教训**：
1. **"我按类别分层了"不算证据，三层校验表才算。** 面试被问"你怎么保证交叉验证没作弊"，
   要给的是"互斥、完备、每图恰好 1 次、test 零泄漏 + 各类偏差 1.5%"，不是一句形容词。
2. **分层的粒度必须说清楚**：它只能控制到样本（图）这一层。凡是"每样本含量不同"的指标（框数、
   实例数、像素数）都会有抖动。要不要按框数分层，取决于**要报的是不是框级指标**——
   本次报 per-class AP，不需要。
3. 图 1595 张、框 3724 个这类**加总自检**（各折相加 = 池子总数）成本一行代码，
   却能一次抓出"重复计入"和"漏掉"两类错误，以后每次都做。

完整表格与判据见 [`交叉验证协议.md`](交叉验证协议.md)。
